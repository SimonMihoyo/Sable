## 一、项目概述

### 1.1 项目背景

随着《个人信息保护法》《数据安全法》等法规的陆续实施，企业面临日益严峻的数据合规压力。当前市场缺少面向中小企业的轻量级数据合规管理平台，本项目旨在填补这一市场空白。

### 1.2 项目目标

| 编号 | 目标 | 度量指标 |
|------|------|---------|
| G-01 | 帮助企业实现数据资产可视化 | 支持自动发现90%以上的数据库存储字段 |
| G-02 | 提供数据分类分级能力 | 内置覆盖PIPL/DSL的分类分级规则集 |
| G-03 | 建立完整的数据访问审计链路 | 审计覆盖率100%，日志保留≥180天 |
| G-04 | 自动化合规差距评估 | 评估报告生成时间 < 5分钟 |
| G-05 | 降低企业合规成本 | 相比纯咨询方案，成本降低60%以上 |

### 1.3 项目范围

**范围内：**
- 数据资产自动发现与清单管理
- 数据分类分级引擎
- 数据访问行为审计
- 合规差距评估与报告生成
- 多租户SaaS平台

**范围外（后续迭代考虑）：**
- 数据跨境传输监控（Phase 3）
- GDPR/CCPA等国际法规支持（Phase 3）
- AI训练数据合规检测（Phase 3+）
- 硬件安全设备集成

### 1.4 术语定义

| 术语 | 定义 |
|------|------|
| PIPL | 《个人信息保护法》(Personal Information Protection Law) |
| DSL | 《数据安全法》(Data Security Law) |
| 个人信息 (PI) | 以电子或者其他方式记录的与已识别或者可识别的自然人有关的各种信息 |
| 敏感个人信息 (SPI) | 一旦泄露或者非法使用，容易导致自然人的人格尊严受到侵害或者人身、财产安全受到危害的个人信息 |
| 重要数据 | 根据《数据安全法》，一旦遭到篡改、破坏、泄露或者非法获取、非法利用，可能危害国家安全、经济运行、社会稳定、公共利益的数据 |
| 数据分类 | 按照数据的业务属性、所属领域等维度对数据进行归类 |
| 数据分级 | 按照数据的重要程度和遭破坏后的影响程度对数据进行分级 |
| 多租户 | 一套系统实例同时服务多个客户（租户），数据逻辑隔离 |

## 二、干系人分析

### 2.1 干系人清单

| 干系人 | 角色 | 关注点 | 影响力 |
|--------|------|--------|--------|
| 企业管理层 (CEO/CTO) | 决策者 | 合规风险、投入产出比 | 高 |
| 合规/法务负责人 | 业务Owner | 法规覆盖完整性、报告可用性 | 高 |
| IT运维/安全团队 | 使用者 | 部署复杂度、系统性能影响 | 中 |
| 业务开发人员 | 间接使用者 | API接入便利性、对业务侵入性 | 中 |
| 监管机构 | 外部 | 报告真实性、合规达标率 | 高 |
| 产品团队 | 建设方 | 产品竞争力、交付节奏 | 中 |
| 开发团队 | 建设方 | 技术可行性、架构合理性 | 中 |

### 2.2 用户角色定义

#### 角色一：系统管理员 (Admin)

- 负责平台配置、租户管理、用户权限分配
- 关注：系统稳定性、配置灵活性

#### 角色二：合规管理员 (Compliance Officer)

- 负责制定合规策略、查看审计报告、发起合规评估
- 关注：规则覆盖度、报告准确性、操作便捷性

#### 角色三：安全审计员 (Auditor)

- 负责查看审计日志、处理异常告警、导出审计报告
- 关注：日志完整性、检索效率、告警准确性

#### 角色四：数据管理员 (Data Steward)

- 负责数据资产确认、分类分级标注、整改跟踪
- 关注：资产发现准确性、分级建议合理性

#### 角色五：普通用户 (Viewer)

- 查看本部门相关的合规状态和报告
- 关注：信息可读性、权限范围清晰

## 三、业务需求

### 3.1 业务流程总览

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│ 数据资产  │───→│ 分类分级  │───→│ 策略配置  │───→│ 访问审计  │───→│ 合规评估  │
│  发现     │    │  标注     │    │  下发     │    │  监控     │    │  报告     │
└──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘
     ↑                                                           │
     └───────────────── 整改反馈 ←── 整改建议 ←──────────────────┘
```

### 3.2 业务需求清单

| 编号 | 业务需求 | 优先级 | 价值说明 |
|------|---------|--------|---------|
| BR-01 | 企业需要全面了解其系统中存储了哪些个人数据 | P0 | 合规基础，不知道有什么数据就无法保护 |
| BR-02 | 企业需要按法规要求对数据进行分类分级 | P0 | 《数据安全法》明确要求，监管检查必查项 |
| BR-03 | 企业需要记录并监控对敏感数据的所有访问行为 | P0 | 《个保法》要求，事后追溯的唯一依据 |
| BR-04 | 企业需要快速评估当前合规状态并获得整改建议 | P1 | 将合规从"凭感觉"变为"可度量" |
| BR-05 | 企业需要生成面向监管的合规报告 | P1 | 监管报送刚需，减少人工编写成本 |
| BR-06 | 企业需要对数据访问异常进行实时告警 | P1 | 事前预防优于事后追责 |
| BR-07 | 企业需要管理第三方数据共享的合规性 | P2 | 供应链安全是监管重点方向 |
